This is the single governing spec for the editor. It replaces every earlier draft and review note; nothing below is superseded by anything else.

## Problem Statement

touch-shortcuts v0.1.0-pre passed its field test (Surface + d&b R1, 10 Nov 2026: default focus tier 1, Up/Down ×10 exact). Every pad change still means hand-editing JSON and tapping ··· → Reload. RadialMenu's worst failure was its config UI, so the editor is where this project wins or loses.

James edits pads in two situations: at home with a keyboard, and at FOH mid-tune with only the pen ("sometimes, you just need to add a button and you don't have a keyboard attached"). He also builds pads for colleagues.

Requested scope:
- Edit each button: label, key combo (recorded or picked by pen), colour, icon, size, repeat.
- A real grid: choose the grid size (e.g. 4×8); buttons cover rectangles (1×3, 2×2); the window resizes to the grid.
- Drag to move/resize; dropping onto a button shoves it aside, like iPhone home-screen icons.
- Pad scale and transparency set in the editor, not by dragging the window corner.
- Background transparency down to 0% ("just floating buttons").

## What Makes This Cool

Every deck editor found (Stream Deck, Bitfocus Companion, ideckia, Stream-Pi, DreamDeck) edits in a separate config window away from the deck. This pad is edited in place: ··· → Edit, and the pad stays where it is, over R1, at its real size. You drag Down ×10 into the corner, record Ctrl+↓ from the Type Cover or pick it with five pen taps, and watch R1's grid show through as you drag the background slider to 0%. The profile file updates as you go, so the pad you just made is already the file you send a colleague.

## Constraints

- The pad window stays non-focusable (Tauri `focusable: false`, focus tier 1). Nothing in this feature may change the pad window's focus behaviour, and the editor panel must not take focus from R1 either (see Edit panel window: activation).
- Pen-first: editor controls (panel buttons, chips, handles, Done) have hit areas ≥ 44 px at every scale. Grid cells may be smaller (the converted R1 profile has 42 px cells), so every drag action has a non-drag alternative that reaches the same result.
- Profiles are shared files: v1 profiles keep loading, unedited, forever.
- Windows first; macOS from the same code (tap-through may use a different mechanism there).
- Rust owns the rules: Rust validates, computes geometry and applies edits; TypeScript renders and forwards pointer input.

## Premises (agreed)

1. **Edit in place.** ··· → Edit puts the pad itself into edit mode; changes apply live and save straight to the profile file. No separate editor app.
2. **Keys are never sent while editing.** A tap selects; `run_action` refuses with `edit-active`. Entering edit mode stops any running action and clears the queue.
3. **Typing needs a focusable surface.** The pad stays non-focusable. Label typing happens in a separate panel window, opened only in edit mode, which activates only when its Label field is tapped or Record starts. Done returns focus to the target app.
4. **Real grid.** The profile declares the grid size; each button has a position and size; empty cells are allowed; the window sizes to the grid. v1 profiles load auto-placed with the same look.
5. **Drag to move/resize; drops shove.** Layout maths in Rust with unit tests. Nudge arrows and size chips/steppers are the non-drag fallback.
6. **Two ways to enter a combo, one result.** Record and the pen picker write the same combo text; the system-key gate still applies.
7. **Scale, pad opacity and background opacity live in the profile:** a shared pad arrives looking as its author set it.
8. **Two opacity controls.** Pad opacity fades the slab and keys, floor 30%. Background opacity 0-100%; at 0% only the keys and the header are drawn, and taps in the gaps reach the app underneath. Keys keep their own backing at every background opacity so labels stay legible over R1.

Premise 8 reverses the 2026-11-08 decision "opaque window, no `transparent`"; its hit-test concern is handled by the window region below, and the spike decides whether it ships.

## Approaches Considered

- **A: Minimal additive editor.** Extra `col`/`row` fields on the v1 format, no tap-through. Rejected: 0% background would block taps in the gaps, and position fields bolted onto flow layout would force a second format change on shared pads.
- **B: Real grid model, separate panel window, tap-through gaps.** Chosen.
- **C: Single window that becomes focusable while editing.** Rejected: bets the field-proven no-focus behaviour on an unverified runtime focusability switch in WebView2.

## Profile format v2

Example (ships as `profiles/example-v2.tsp.json` and is loaded by the shipped-profiles test):

```json
{
  "$schema": "../schema/tsp-v2.schema.json",
  "schema": 2,
  "name": "R1 numpad 4x8",
  "acceptTouch": true,
  "pad": {
    "grid": { "columns": 4, "rows": 8 },
    "cellWidth": 69, "cellHeight": 76, "gap": 8,
    "scale": 1.0, "padOpacity": 1.0, "backgroundOpacity": 0.97,
    "dock": "right", "theme": "c-low-glare"
  },
  "buttons": [
    { "id": "d7", "label": "7", "x": 0, "y": 0, "w": 1, "h": 1, "group": "num",
      "action": { "type": "keys", "combo": "Num7" } },
    { "id": "enter", "label": "Enter", "icon": "enter", "x": 0, "y": 4, "w": 2, "h": 2, "group": "ent",
      "action": { "type": "keys", "combo": "Enter" } }
  ]
}
```

- Size convention everywhere (format, chips, steppers, this doc): **w×h = columns × rows**. "1×3" is one column wide, three rows tall.
- Bounds, chosen so every valid v1 profile converts exactly: `columns` 1-12; `rows` 1-60; `cellWidth` 8-200 (integer); `cellHeight` 40-200; `gap` 0-24; `scale` 0.5-2.0, snapped to hundredths before validation (ten +0.1 steps from 1.0 reach exactly 2.0); `padOpacity` 0.3-1.0; `backgroundOpacity` 0.0-1.0; 0-60 buttons; every button fully inside the grid with `w`,`h` ≥ 1; no two buttons overlap (load error `profile-overlap` naming both ids and the shared cell). Per-button rules (id, label, colour, combo, repeat, interval, icon, group) are unchanged from v1. A v2 file containing `opacity` instead of `padOpacity` raises the near-miss warning.
- `backgroundOpacity` below 0.05 is treated as 0 everywhere: the slider writes 0, the loader normalises a hand-edited 0.01-0.049 to 0 (logged as `edit-op kind=normalise`) and the normalised value is written on the next save.
- New action type `{ "type": "none" }`: a button not assigned yet. It renders with a "+" glyph and dashed border and sends nothing; a tap outside edit mode flashes "Not set: ··· → Edit".
- v2 accepts 0-60 buttons. An empty pad shows the header and "Empty pad: ··· → Edit to add buttons" (in edit mode: "Tap a cell to add a button"). v1 files keep their 1-60 rule.
- `$schema`: `schema/tsp-v2.schema.json` is generated from the Rust types (`schemars`) and ships with the release; a test checks it accepts every shipped v2 profile.

### v1 → v2 conversion (on load)

- `columns = gridColumns`; `cellWidth = (buttonWidth − gap) / 2` with integer division, as v1 computes its column width (minimum (40 − 24) / 2 = 8); `cellHeight = buttonHeight`; each button becomes `w = span, h = 1`, placed in reading order exactly as v1 flowed them; `rows` = rows used (at most 60).
- Rendering goes through the same fit rule as v1 (below), so the pad looks identical. Tests cover buttonWidth 40 with gap 24, gridColumns 1 with 60 buttons, and the shipped R1 profile (golden).
- The converted v2 document is the undo baseline; undo never writes v1.

### First-edit rewrite of a v1 file

- v1 files are rewritten only on the first edit. The original is copied first to `<file name>.v1.bak` beside it. An identical existing backup is kept; a differing one leads to `<file name>.v1.<n>.bak`. A backup is never overwritten.
- A failed backup copy aborts the rewrite and reverts the op: `profile-backup-failed: couldn't copy <path> to <bak> (<os error>). Nothing changed. Make the folder writable, or use New pad.`
- The rewrite drops v1-only fields (`gridColumns`, `buttonWidth`, `buttonHeight`, button `span`). A `$schema` whose value contains `tsp-v1` is replaced with the v2 schema; any other `$schema` value is kept.
- The first rewrite shows once: "Saved as format v2 (needs v0.2). Backup: <name>.v1.bak". v0.1 builds reject schema 2 with the "newer version" hint, which includes the releases URL.

### Round-trip preservation and saves

- `tsp-core` enables `serde_json/preserve_order`. Each button keeps its original JSON object; every op patches the raw document by button id, serializes, reloads through the loader and diffs. Unknown fields (top level, `pad`, buttons, actions) are written back unchanged, as are values the loader replaced for display (unknown group, dock, theme, icon) and the raw action of every disabled button (a system key blocked on this machine, an action type from a newer version).
- Saves are atomic (temp file + rename), 2-space pretty-printed with a trailing newline. Golden text test: one label edit on the shipped profile changes exactly one line.
- Round-trip test: edit a different button in a profile containing a blocked `Win+R` and an unknown action type; both survive byte-for-byte as JSON values.
- A serialized document over the 256 KB cap is refused with `profile-too-large`.

## Geometry: fit to the screen

- Natural size = grid at `cellWidth × scale`, `cellHeight × scale`, `gap × scale`, plus padding and header (both also × scale), computed in f64 logical px and rounded once.
- **Height (v1's rule, kept exactly):** if the natural height exceeds work-area height − 24 px, all rows shrink evenly to fit; if the fitted row is under 56 px, rows render at 56 px. This includes v1's quirk: an overflowing profile whose cells are under 56 px renders 56 px rows. Test: a v1 profile with buttonHeight 40 at a work area that forces overflow renders 56 px rows in both v1 and v2.
- **Width (new in v2; v1 never clamped width):** width never shrinks. A pad wider than the work area − 24 px, or still too tall at the 56 px floor, is clamped to the work area: the right columns or bottom rows are clipped, with an amber warning that names the actual and allowed sizes and says "lower scale, rows or columns". Test: a pad wider than the work area.
- The 56 px floor and every ≥ 44 px editor hit area are not scaled. Tests at scale 0.5 and 2.0.
- Golden test: the shipped v1 R1 profile, converted, renders exactly v1's rects at work-area heights 912 px (rows shrink to 74 px) and 2000 px (natural 78 px).
- **Edit mode** adds a 44 px margin around the grid and a header at least 44 px tall at any scale. Both are inputs to the fit rule (rows shrink again; the 56 px floor still applies; the clamp warning shows if it still doesn't fit). Edit mode is therefore not pixel-identical to normal mode. Test: shipped R1 profile at a 912 px work area in edit mode, and scale 0.5 in edit mode.
- The window position is a stored logical anchor on `current_monitor()`. Layout changes keep the docked edge; a pad that would grow past the work area is shifted back inside it.

## Layout engine (`tsp-core::layout`, pure, tested)

`place(grid, buttons, mover, target) -> Result<Vec<Button>, LayoutError>`, where `target` is the mover's new rect (move or resize).

1. `target` must lie inside the grid, else `layout-out-of-grid` (the UI clamps drags before calling).
2. **Victims** = buttons other than the mover whose rect intersects `target`, ordered by top-left (row, then column).
3. **Free cells** = all grid cells, minus cells of non-victim buttons, minus `target`. The mover's vacated cells and the victims' own old cells count as free.
4. For each victim in order: if its unchanged w×h fits entirely inside the mover's still-free vacated cells, it takes the top-left-most such position (the home-screen swap). Otherwise the candidates are every top-left where it fits entirely in the free cells; pick the smallest Manhattan distance between old and new top-left. Among equal distances, sort by the tuple `(dy <= 0, dy < 0, dx != 0, dx < 0, new_row, new_col)` ascending, which yields straight below, below-right, below-left, right, left, straight above, above-right, above-left. Place it and remove its cells from the free set.
5. If a victim has no candidate, retry once with victims ordered by descending area. If that also fails, refuse with `layout-grid-full` and move nothing.
6. Non-victims never move; there is no cascade. Each victim is placed exactly once.

Worked examples, one test each (grid 4×8, positions (x,y)):
- Move into empty cells: A 1×1 at (0,0) → (3,7) empty. No victims; A moves.
- Drop onto a 1×1: A (0,0) → (1,0) where B is 1×1. B fits in A's vacated cell: B goes to (0,0), a swap.
- Drop a 1×1 onto a 2×1: A 1×1 (3,7) → (0,0) where B 2×1 covers (0,0)-(1,0). B doesn't fit in A's vacated cell, so it takes the nearest free fit: (0,1) if (0,1) and (1,1) are free (distance 1, straight below).
- 2×2 onto two 1×1s: E 2×2 at (2,6)-(3,7) moves to (0,0)-(1,1), where B (0,0) and C (1,0) sit. Victims B, C. B fits in E's vacated cells, top-left-most (2,6); C then takes (3,6). Result: E (0,0), B (2,6), C (3,6).
- Grid full, refused: every cell occupied; B 2×1 covers (0,0)-(1,0), C covers (2,0), A 1×1 at (3,7). Drop A onto (0,0). Free = {(3,7), (1,0)}. No two horizontally adjacent free cells, so refused; nothing moves.
- Grid full, adjacent case succeeds: same grid but A at (2,0) (C elsewhere). Drop A onto (0,0). Free = {(1,0), (2,0)}. B fits at (1,0) (distance 1, right).
- Tie-break at distance 2: (0,+2) beats (+1,+1); one test per adjacent pair of the tie-break order.
- Shrinking the grid is refused with `layout-button-outside-grid`, naming, selecting and outlining the first button that would fall outside; the message offers "Select it". Nothing moves automatically.

Property test (seeded loop): no overlaps, everything inside the grid, non-victims unchanged, ids preserved, a refused op leaves the document byte-identical, a drop on the origin adds no undo step.

## Edit operations and state

- **Commands:** `edit_apply(op)` applies an op; `edit_preview(op)` is read-only and uses the same `place` code (the drag ghost and shove preview); `get_editor_state` returns the full state. `edit_begin`, `edit_done`, `pads_switch`, `pad_new` and every save path are async commands; the editor window is never built from a sync command (WebView2 deadlock). Windows CI smoke test: open and close the panel without hanging.
- **Ops:** `move`, `resize`, `set_label`, `set_action`, `set_color`, `set_icon`, `set_group`, `add`, `duplicate`, `delete`, `set_pad` (grid, scale, padOpacity, backgroundOpacity, cell size, name). Every op carries `button_id` (where it applies) and `base_rev`; a stale rev is refused with `edit-stale`. Events carry `rev` and the webviews drop older ones. Every result runs through the same validator as file loading; an op that would disable the edited button or raise the warning count is refused (pre-existing disabled buttons are exempt).
- **State:** one `EditorState` (active flag, raw doc, undo stack, rev, save state, return target) behind one mutex, never held across window calls; edit-path locks are poison-tolerant and `edit_apply` runs under `catch_unwind`. `tsp-core::edit` is pure (raw doc in, raw doc out; no file system or clock) and tested with fakes like `executor.rs`. App-side editing, saving, the watcher and the pads list live in `src-tauri/src/editing.rs` and `src-tauri/src/pads.rs`.
- **Edit gate:** the `editing` flag lives in `Shared` under the queue lock; `run_action` checks it in the same critical section as `queue.tap`; `edit_begin` sets it and stops everything atomically. Test: a tap after begin is refused with `edit-active: nothing sent. Tap Done to use the pad.`
- **add:** a `none` button labelled "New" at the selected empty cell ("+ Add here") or, from "+ Add button", at the first free cell in reading order. Size = the pad's most common button size (2×1 on converted v1 pads), falling back to 1×1 where that doesn't fit. Id `btn-N`, smallest unused N. On a full grid with fewer than 60 rows, a row is added and the button placed there in one undo step, with "No empty cell: added row <n>". Otherwise `layout-grid-full`. Over 60 buttons: `edit-max-buttons: this pad has 60 buttons (the maximum). Delete one first.` Test on the shipped R1 pad: add grows row 11 and the new button is 2×1.
- **duplicate:** copies every field except id and position. Id = base trimmed so the suffix survives (`base[..32 − suffix.len()] + suffix`, suffix `-2`, `-3`, ...; tested with a 32-character id); position = nearest free fit by the layout distance rule; no fit → `layout-grid-full`.
- **Duplicate as <mirror>:** shown when the selected button's key has a mirror (Up/Down, Left/Right, PageUp/PageDown, Plus/Minus). It swaps the key, swaps only that key's word pair in the label, whole-word and case-preserving ("Ctrl+Up" → "Ctrl+Down", "Up ×10" → "Down ×10", "Upper" unchanged; "+"/"−" only when they are the whole label), and swaps only the matching icon pair (up/down for Up/Down keys, left/right for Left/Right keys; a Left key with an "up" icon keeps "up").
- **delete:** removes the selected button; an empty pad is allowed. The panel shows "Deleted '<label>' · Undo edit" until the next op or 5 s; tapping it undoes only while that delete is still the latest snapshot.
- **Labels:** a button's label follows its combo (e.g. "Ctrl+↓ ×10") until the user types one. Typed labels commit on Enter, on blur, after 600 ms without typing, or when Done is tapped. While empty or over 24 characters, the field shows an inline message and nothing commits. Consecutive label commits on one button within 2 s form one undo step. Auto-labels shrink to 11 px after scale, then drop modifiers, then ellipsis.
- **set_action** only commits a complete action. Choosing Keys on a `none` button keeps `none` until a key is picked; "Clear" sets `{ "type": "none" }`.
- **Disabled buttons** (blocked system key, unknown action type): label, colour, icon, size and position stay editable; the Action section shows the reason read-only with "Replace", which opens the Keys picker. The raw action JSON is kept until replaced.
- **Same-combo warning:** combos are compared parsed (modifier set + key) plus repeat, so `Shift+Ctrl+Up` equals `Ctrl+Shift+Up` and aliases match. The panel shows "Same keys as '<label>' (row <n>)" (1-based row, "(+N more)" for several); the edit is allowed.
- **Undo/redo:** snapshot stack in Rust, capped at 100, cleared whenever the active profile changes (Pads, New pad, Reload), so an undo can never write one pad's content into another pad's file (tested). Labelled "Undo edit" / "Redo edit" (the pad's own Undo/Redo keys send Ctrl+Z / Ctrl+Y to R1). Ctrl+Z / Ctrl+Y undo and redo edits while the panel has focus. "Revert to when I tapped Edit" (Pad tab, inline confirm) restores the edit-begin snapshot as one undo step.
- Each op's result is emitted as `pad-changed` to both windows; selection lives in Rust and is emitted as `selection-changed`, so pad and panel never disagree.

## Saving, conflicts and failures

- **Ordering:** ops, saves, flushes and reloads share one mutex. Saves happen after each op; slider drags are debounced (300 ms). Done, Quit, Reload and any pad switch commit a pending valid label and flush a pending save first. The file's identity (mtime, size, content hash) is recorded after every write. Fake-clock/fake-fs tests: debounce coalescing, save-then-op, hand-edit between writes.
- **Change detection:** before each save the file identity is compared with the last load or save. Own writes are suppressed. Outside edit mode a changed profile reloads automatically (watch the parent directory with `notify`, debounced 500 ms, same rules as Reload: the queue stops first and the pad shows "Reloaded from disk"). The watcher is off while editing. `"watchProfile": false` in `settings.json` turns it off entirely.
- **Conflict (file changed on disk while editing):** edit ops are blocked; the header reads "EDITING · paused: file changed on disk" and the panel offers **"Keep my edits (overwrite file)"** (force-write, record the new identity) or **"Load file (discard N edits)"** (discard in-memory edits, clear undo, load the file). Done, Quit, a pad switch and a panel close request (including Alt+F4, which is vetoed) first show the same choice. Keep my edits, or a successful Load file, continues the action that triggered it. A Load file that fails to load keeps the in-memory pad, shows the load error, leaves the conflict open and cancels the triggering action. A failed force-write follows the save-failure path. Tests for each branch.
- **Save failure:** `profile-save-failed: couldn't save <path> (<os error>). Your edits are kept in memory; the file is unchanged.` with Retry and "Save as new pad". Up to 3 automatic retries with backoff, then a retry on each op. Done and Quit with unsaved edits ask "Unsaved edits: Retry / Save as new pad / Discard" and never exit silently. Fake-fs tests for retries and the prompts.
- **Session end** (logoff/shutdown) is never vetoed: unsaved in-memory edits are written to `<name>.unsaved-<time>.tsp.json` beside the original, falling back to the app config dir. On Windows a separate subclass id handles only `WM_QUERYENDSESSION`/`WM_ENDSESSION` (`DefSubclassProc` otherwise), under `catch_unwind`, with `try_lock` and a timeout.
- `settings.json` is read-modified-written as a raw JSON value preserving unknown keys, and never written after a failed read.

## Entering and leaving edit mode

- ··· → Edit is unavailable on a fallback pad: the item reads "Edit (fix the profile error first)". New pad and Pads stay available there (see below).
- **Entering:**
  - Stops any running action and clears the queue. If an action was cancelled part-way, the message slot keeps "Stopped <label> at n/N: value changed by n" until the next op, and it is logged.
  - Captures the return target: Windows `GetForegroundWindow()` if it is not the pad (tapping ··· leaves R1 in front), else `LAST_OTHER`; macOS the frontmost app, else the tracked last other app.
  - Opens the panel without activating it. If panel creation fails, the pad stays in normal mode with `editor-open-failed: <tauri error>. See actions.log.` (logged as `edit-begin result=failed` with the error chain); the next ··· → Edit retries.
  - Edit mode opens with nothing selected, on the Pad tab: "Tap a key to edit it, or an empty cell to add one". A Blank preset also highlights the first empty cell.
- **Done** (header button, panel Done, or the panel closing by any means):
  - Commits a valid pending label, flushes any pending save (conflict and unsaved-edit prompts first).
  - Restores the captured target **before** the panel closes: Windows `SetForegroundWindow` if `IsWindow` is still true; macOS public `tsp_mac::activate(pid)`. Then verifies the foreground (Windows `GetForegroundWindow() == target`; macOS frontmost pid). On mismatch or a vanished target: amber `restore-failed: couldn't return to "<title>". Tap it before using the pad.` (side effects none; logged `edit-done restore=failed`). Test with a fake foreground that refuses activation.
  - Closes the panel and leaves edit mode.

## New pads and switching pads

- "New pad": pick a preset ("R1 numpad 4×8", a new layout with the shipped R1 keys; "Blank 4×8"; "Blank 3×10"; blank presets have zero buttons). Written to the app config dir as `pad-N.tsp.json` (smallest unused N), named "New pad N" (rename in the Pad tab), made active, `settings.json` `lastProfile` updated, edit mode entered. Write failure: `pad-create-failed: couldn't write <path> (<os error>). Current pad unchanged.`
- "Pads": a pen list of the `*.tsp.json` files in the app config dir plus the last opened path, built in Rust. Rows show name, file name and a check on the current pad; broken files are marked amber "Can't open: <code>". Commands take an index into the Rust-built list, never a path from the webview. Tapping a row switches to it (staying in edit mode if already in it). A file that fails to load is refused: the current pad stays active and the error ends "Fix the file, then pick it again in Pads". Switching never lands on a fallback pad.
- New pad and Pads are in the ··· menu as well as the Pad tab, so they work outside edit mode and on a fallback pad. New pad always writes a new file, so a broken file is never overwritten.
- "Show file" (opener reveal) is how a pad goes to a colleague; it notes "This pad needs touch-shortcuts v0.2 or later".

## Pad window in edit mode

- Header: "EDITING · <profile name>" with Done (≥ 44 px hit area at every scale). The status row shows the selection. ··· in edit mode lists Done, Pads, New pad, Reload, Quit (each flushes first).
- Edit mode previews pad opacity 1.0 and background ≥ 0.6, except while an opacity slider is being dragged. Unselected keys are dimmed by outline, not alpha. Empty cells are drawn dashed.
- The selected key has a bright outline with a corner notch and **one resize handle at its bottom-right corner**: a 44×44 px hit square placed entirely outside the key, with its top-left at the key's bottom-right corner, drawn as a 16 px triangle. The whole key body always means move. The handle wins over anything under it (gap, neighbouring corners); only the selected key has one. The 44 px edit margin keeps it reachable at the grid's right and bottom edges.
- **Drag:** starts after 8 logical px and only on the selected key; pointer capture; second pointers are ignored during capture; `pointercancel` reverts. The ghost snaps to the cell under the pointer. The shove preview (`edit_preview`) recomputes after a 120 ms dwell and animates 120 ms (off under `prefers-reduced-motion`). A refused target draws the ghost in `--red` with a cross and "No room". Outside the grid: "Release to cancel". Drop on the origin is a no-op with no undo step. Release commits `move`/`resize`. The panel hides during a drag (`SW_HIDE`) and returns on drop (`SW_SHOWNOACTIVATE`).
- Tapping a key selects it. Tapping an empty cell selects that cell. Tapping the header selects the pad (no cell).
- Finger input works in edit mode regardless of `acceptTouch` (which only governs sending keys); palm filters stay on.
- Edit-mode tokens live in `src/styles.css`: selection outline and notch, dashed empty cell, ghost, victim preview, refused, handle triangle; low-glare and contrast-checked.
- The pad window stays non-focusable throughout.

## Edit panel window

- A second Tauri window (`editor`, `editor.html` + `src/editor.ts`): frameless, theme C, about 350 px wide, created on Edit, destroyed on Done. Its 44 px title strip is the drag region. Labels are set with `textContent` only.
- **Activation:** created with `focus: false` and `WS_EX_NOACTIVATE` (via `tsp-win`). Taps on pen controls never activate it. It becomes activatable and foreground only when the Label field is tapped or Record starts. As soon as the label commits (Enter, tapping away, the 600 ms pause) or Record ends, it returns to no-activate and gives the foreground straight back to the captured target, not only at Done: the spike showed that while our panel is in front, a tap on the pad makes the pad the foreground window. While the Windows touch keyboard (InputPane) is docked, the panel moves up so the Label field stays visible.
- **Placement:** beside the pad on whichever side has at least 350 px, preferring the side away from screen centre. If neither side has room, it overlaps the half of the pad away from the selected key and its header shows "Swap side" (44 px). The position is locked after first placement and changes only on Swap side, on ‹ › selecting a covered key, or when a settled change makes it overlap. Height = min(pad height, work area − 24 px).
- **Tabs:** Button and Pad. Tabs auto-switch only when the selection kind changes (key → Button; empty cell or pad → Pad); manual switching is always allowed and the selection persists.

### Panel layout (governs the panel)

Top to bottom; only the middle region scrolls:

1. **Sticky top block:** selection "‹ n of N ›" (previous/next key in reading order, for cells too small to tap), live combo summary ("Ctrl+Down ×10, every 25 ms"), same-combo warning, message slot (refusal copy, notices; stays until the next op).
2. **Button tab, scrolling middle (Action section):** a static "Keys" caption (the action-type selector renders as a caption until a second type exists); modifier row (Ctrl, Shift, Alt, Win toggles, which persist and commit with the key); page tabs Nav (← ↑ ↓ → Home End PgUp PgDn) · Edit (Enter Tab Esc Space Backspace Delete) · Digits (0-9 . Comma) · Numpad (Num0-Num9 NumDecimal Plus Minus) · F-keys (F1-F12) · Letters (A-Z), with **Record** as one button in the page-tab row; the key grid; repeat chips ×1 ×4 ×10 and "Custom…" (stepper 1-50). An existing combo opens its key's page with its modifiers pre-toggled. "Clear" and, for disabled buttons, the read-only reason with "Replace".
3. **Collapsible "Size & position":** chips 1×1, 2×1, 1×2, 2×2, 3×1, 1×3; W and H steppers reaching every size the grid allows (each step is a `resize` op); a "Move" direction pad (each step is a `move` op).
4. **Collapsible "Look":** Label first, colour swatches (44 px, one per theme group plus Default; a hex colour from JSON shows as "Custom"), icon grid (the existing `ICONS` set plus None).
5. **Sticky footer:** Duplicate / Duplicate as <mirror>, Delete, Saved status ("Saved · just now").

Nothing on the success path (select key → pick modifiers and key → repeat) needs scrolling past the key grid at a 912 px work area.

**Record:** armed state shows "Press the keys…" and Cancel replaces Record. It commits on the first non-modifier keydown with the held modifiers; Esc and Enter are recordable; it ends unchanged after 10 s or on blur. `KeyboardEvent.code` maps to the grammar in `tsp-core::combo` (table test): Digit0-9 and Period map to the number-row keys. Codes with no grammar key show "<key> isn't supported: pick it with the pen" and stay armed. Win combos are pen-only (Windows consumes them); a timeout after a Win keydown says "Win combos: pick them with the pen".

**Pad tab:** when an empty cell is selected, a "Cell (x, y)" block at the top with "+ Add here" (full width; selects the new button and opens the Button tab on the Keys page) and "Move <label> here" (when a key was selected just before). Then: Name; scale stepper (− 1.0 +, 0.1 steps); grid columns × rows steppers; pad opacity (floor 30%); background opacity with "Floating: taps in gaps reach the app below" and "Taps pass through after Done" beside it when it is 0; New pad, Pads, Show file, "+ Add button", Undo edit, Redo edit (disabled at 40% when empty), Revert to when I tapped Edit; Done.

- `layout-grid-full: no room for "<label>" (<w×h>). Nothing moved. Add a row, or shrink or delete a button.`
- `layout-button-outside-grid` names the blocking button with "Select it".
- `edit-max-buttons`, `pad-create-failed`, `profile-save-failed`, `profile-backup-failed`, `restore-failed`, `editor-open-failed` as written in their sections.

## Scale and transparency

- Scale multiplies cell sizes, gap, padding and header height before the fit rule; fonts scale through a CSS variable.
- The pad window is created transparent (`transparent: true`, transparent webview background; macOS needs Tauri's `macOSPrivateApi` / `macos-private-api` feature, fine outside the App Store).
- Pad opacity applies to the slab and keys only. The header (both rows) and the open ··· menu are always drawn at full opacity with a backing of at least 0.9 alpha, so status and safety messages stay legible at every setting. Background opacity is the alpha of the slab; keys keep their own backing at every background opacity.
- **Tap-through, Windows:** at background 0, outside edit mode, the window gets a region (`SetWindowRgn`) equal to the union of the key rects, the header (both rows) and the open menu.
  - Outside the region the window does not exist, so pen, finger and mouse taps reach R1 natively, with no cursor polling.
  - The region is built from the same f64 logical rects × the current scale factor, rounded outward to device pixels; a pure builder in `tsp-core` is tested at 1.0, 1.25, 1.5, 1.75 and 2.0, and for header, menu and status-row states.
  - It is rebuilt on every layout change, scale-factor change, monitor move, ··· menu open/close and status-row size change. The menu opens region-first (invoke, await, then unhide). Rust clamps webview-supplied rects to the window and caps their count. Rebuilds are skipped when geometry is unchanged; the HRGN is deleted only when `SetWindowRgn` fails and is re-applied after resize.
  - Window shadow and rounded corners are off while the key-only region is active.
  - In edit mode, and above background 0, the region is the full pad rect.
  - If `SetWindowRgn` fails: background renders at max(file value, 0.30) with `region-unavailable: <err>. Background shown at 30% until restart.` and a `region mode=fallback` log line.
- **Tap-through, macOS:** first try the system's pass-through of fully transparent pixels in a non-opaque window; if WKWebView blocks it, toggle `ignoresMouseEvents` from cursor position. Lower priority than Windows.
- **Escape hatch:** `--window=opaque`, `TSP_WINDOW=opaque` or `"window": "opaque"` in `settings.json` forces the opaque window path (as the opaque spike outcome below).
