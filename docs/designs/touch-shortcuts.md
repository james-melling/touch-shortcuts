# Design: touch-shortcuts, a stylus button pad for system tuning

Generated by /office-hours on 2026-11-08
Branch: james-melling/office-hours
Repo: james-melling/touch-shortcuts
Status: APPROVED (office hours 2026-11-08; /autoplan final gate 2026-11-09)
Mode: Builder

## Problem Statement

System techs tuning PA systems on a tablet PC (usually a Microsoft Surface) operate d&b R1 and Meyer Compass with a stylus. To avoid the keyboard they float a pad of big buttons on the right edge of the screen that send keystrokes to the app behind it. Today that pad is RadialMenu (radialmenu.weebly.com), which is old and effectively unsupported. James, his team and other colleagues all use it.

RadialMenu's keystroke sending works. Everything around it fails:
- hard to install
- the button config menus are badly designed
- portable config files are unreliable
- no OSC support
- the interface looks like it's from 2004

Reference pad (James's real layout): `0`-`9`, `Enter`, `Up`, `Down`, `Tab`, `Ctrl+Up`, `Ctrl+Down`, `Up x10`, `Down x10` (10 quick presses), plus assignable Undo/Redo.

## What Makes This Cool

- Every Stream Deck-style tool we found (Macro Deck, TouchDeck, StreamPi, TouchPortal) puts the buttons on a second device; same-screen tools like Tablet Pro and Elgato's on-screen deck are untested against R1 (check after Tuesday). This one is built for **one machine, one pen, with the target app always visible under the pad**. Nothing open source covers that well.
- Shareable profiles: the crew sends a pad as one file, and the project ships starter pads for R1 and Compass that work on first launch.
- Setup by demonstration: tap a button, press the real key combo, drag the corner to resize. A new pad takes two minutes.
- Same action model for keys, OSC and QLab cues, so a pad can tune the PA, then nudge a console parameter or fire a cue.

## Constraints

- **Field test Tuesday 10 Nov 2026** on a real system tune (Surface + R1). RadialMenu stays installed as the fallback.
- Windows first; macOS must follow from the same codebase (R1 and Compass both run on Mac).
- Must never take focus away from R1/Compass, or the keystrokes land in the pad instead.
- Pen-first: large targets, works in a dark FOH (front of house) environment.
- Open source; colleagues install it themselves.

## Premises (agreed)

1. RadialMenu's failures are setup: install, button editor, profile portability, looks. Sending keys works. We win on setup, and sending keys without stealing focus is the bar we must pass.
2. Pad lives on the same screen as R1/Compass, operated by pen. No second device. The phone remote was rejected: "you wouldn't be able to see what you were interacting with."
3. Tuesday is a field test: Windows only, the 18 buttons, profile loaded from a file. The polished editor and Mac build come after.
4. Every button runs an *action* from day one (key combo, key combo xN, later OSC / QLab cue), so pages, OSC and QLab are additions, not rewrites.
5. A profile is one readable JSON file; copying the file is the portability.
6. The stack must support Windows and macOS; installers ship through GitHub Releases.

## Approaches Considered

### Approach A: Native Windows first (C# / .NET 8 WPF)
Fastest, lowest Tuesday risk. Rejected: breaks premise 6 (macOS becomes a second app or a hard port) and a WPF editor tends to look dated.

### Approach B: Tauri 2, cross-platform from day one (CHOSEN)
Rust core for key sending and OSC, web UI for the pad and editor, non-focusable window. Effort M (human ~1-2 weeks / CC ~4-6 h for Tuesday scope).

### Approach C: AutoHotkey for Tuesday, Tauri afterwards
Near-certain Tuesday, but the AutoHotkey script gets thrown away. (Antivirus heuristics can flag any unsigned exe that injects input, Tauri included; signing is a Phase 2 requirement.) Rejected in favour of building the real thing now, with RadialMenu as the Tuesday safety net.

### Approach D: Control the devices over the network instead of the GUI (not chosen)
Driving amps/processors via their network protocols would remove the focus problem entirely, but protocol coverage varies by vendor, techs think in the R1/Compass interface, and a keystroke pad works with any app. Generic OSC (Phase 3) is not this.

## Recommended Approach: Tauri 2

**Stack**
- Tauri 2 (Rust) + Vite + TypeScript frontend (no UI framework for Tuesday; choose one when the editor is built).
- Key sending: Windows `SendInput` via the `windows` crate (explicit VK codes and extended flags); `enigo` for the macOS sink (Phase 2).
- OSC (phase 3): `rosc` crate over UDP.
- Window: created with `visible: false`, styles applied, then shown with `ShowWindow(SW_SHOWNOACTIVATE)` on the raw HWND (a normal show can activate a freshly launched process); every `SetWindowPos` (always-on-top toggle, re-dock, resize) carries `SWP_NOACTIVATE`; after the Open profile… dialog closes, the previous foreground window from the hook is restored; `decorations: false`, `alwaysOnTop: true`, `focusable: false`, `skipTaskbar: true`, docked on every launch to the right edge of the primary monitor's work area, 12 px from the edges; the window is sized to its content (see Pad UI specification: height policy) and covers only what it draws; it overlays the target app rather than reserving screen space (position memory is deferred, E9).

**Focus strategy, in three tiers** (the spike decides which one ships):
1. Tauri `focusable: false` (added Aug 2025, PR #13564).
2. If the pen tap still activates the window (WebView2 hosts its own child window, which may take focus): get the raw HWND from Tauri, apply `WS_EX_NOACTIVATE` to the top-level window and return `MA_NOACTIVATE` on `WM_MOUSEACTIVATE`/`WM_POINTERACTIVATE` via a top-level subclass (the WebView2 input window lives in `msedgewebview2.exe` and cannot be subclassed; the spike only records whether setting the style on it helps). About 30 lines of Rust with the `windows` crate; the subclass wndproc never panics (an unwind out of `extern "system"` aborts the process). If tier 2 fails, the post-Tuesday candidate before accepting tier 3 is tier 2b: a native input-only `WS_EX_NOACTIVATE` layered window over the keys, hit-tested in Rust from the profile geometry, with visual state sent to the web layer by event.
3. Last resort: track the last non-pad foreground window (`SetWinEventHook(EVENT_SYSTEM_FOREGROUND)`), and before each send restore it (`SetForegroundWindow`) then `SendInput`.

Drag: a small grip strip uses Tauri's `startDragging`; if that fails with no-activate set, drop the style temporarily during the drag, like the Windows on-screen keyboard.

**Profile format v1** (`*.tsp.json`):
```json
{
  "schema": 1,
  "name": "R1 - Delay/Gain",
  "acceptTouch": true,
  "targetApps": ["R1.exe"],
  "pad": { "gridColumns": 6, "buttonWidth": 92, "buttonHeight": 78, "gap": 8, "dock": "right", "theme": "c-low-glare" },
  "buttons": [
    { "id": "d7", "label": "7", "span": 2, "group": "num", "action": { "type": "keys", "combo": "Num7" } },
    { "id": "enter", "label": "Enter", "span": 6, "group": "ent", "action": { "type": "keys", "combo": "Enter" } },
    { "id": "down10", "label": "Down", "icon": "down", "span": 3, "group": "coarse",
      "action": { "type": "keys", "combo": "Down", "repeat": 10, "intervalMs": 25 } },
    { "id": "undo", "label": "Undo", "span": 3, "group": "hist", "action": { "type": "keys", "combo": "Ctrl+Z" } }
  ]
}
```
Defaults: `repeat` = 1, `intervalMs` = 25, `span` = 2, `acceptTouch` = true (pen, mouse and finger all fire; a profile can set false for pen-only), `targetApps` = none (any app), `theme` = `c-low-glare`. `targetApps` lists foreground process image names the pad may type into; a mismatch refuses with `target-not-allowed` (the R1 exe name is confirmed on the Surface before Tuesday). System keys are allowed only by the local `settings.json` (`"allowSystemKeys": true`), never by a profile, so a shared pad cannot enable them.
Validation (Rust, on load): `schema` must be 1 (higher: "profile needs a newer touch-shortcuts"); `gridColumns` 1-12; `span` 1..`gridColumns`; `buttonWidth`/`buttonHeight` 40-200 px; `gap` 0-24; 1-60 buttons; `id` required, unique, `[a-z0-9-]{1,32}`; `repeat` 1-50; `intervalMs` 10-1000; `color` `#RRGGBB`; `label` required, 1-24 chars; `name` 1-48 chars; `dock` is `"right"` or `"left"` (other values ignored with a warning); unknown `theme` falls back to the default with a warning; unknown `group` renders as `custom`. Structural errors reject the profile; an unknown key name or action type disables only that button. Parsing: `serde_json::Value` first (line/column for syntax errors), then each button converts from `Value` to typed structs individually so errors are collected per button; every struct carries `#[serde(flatten)] extra` to collect unknown fields; bounds live in type attributes so the `schemars` schema and the validator share one source, and a test checks the generated schema accepts every shipped profile. `$schema` is allowlisted; other unknown fields are info-level (logged) unless within edit distance 2 of a known field (e.g. `intervalMS`), which raises an amber warning naming the field.
Sizing: `buttonWidth` is the width of a standard span-2 key; one column = (`buttonWidth` − `gap`) / 2; pad inner width = (`gridColumns` / 2) × `buttonWidth` + (`gridColumns` / 2 − 1) × `gap` (6 columns, 92, 8 → 292 px + 2×10 px padding ≈ the approved 318 px mockup incl. border).
Key timing: one press = one `SendInput` batch [modifiers down, key down, key up, modifiers up]; modifiers are pressed per repeat, never held across repeats; `intervalMs` is start-to-start. Optional `color` overrides the theme's group colour. Combo grammar: `Mod+Mod+Key`, modifiers `Ctrl|Shift|Alt|Win`, keys `0-9`, `A-Z`, `.`, `Minus`, `Plus`, `Comma`, `Num0-Num9`, `NumDecimal`, `Enter`, `Tab`, `Esc`, `Space`, `Backspace`, `Delete`, `Up|Down|Left|Right`, `Home|End|PageUp|PageDown`, `F1-F12`; case-insensitive, whitespace around `+` trimmed, aliases `Control`→Ctrl, `Return`→Enter, `Escape`→Esc, `Del`→Delete, `ArrowUp/Down/Left/Right`→arrows, `-`→Minus. System-key gate (local `settings.json` only) covers exactly: any combo with `Win`, `Ctrl+Esc`, `Alt+F4`, `Alt+Tab`, `Alt+Esc`, `Alt+Space`, `Ctrl+Shift+Esc`. Layout: number-row digits, `.` and OEM keys depend on the active keyboard layout (AZERTY types `&` for VK `1`), so starter profiles use `Num0`-`Num9` (`VK_NUMPAD*`, layout-independent; NumLock does not affect injected VKs); `Plus` = `VK_ADD`, `Minus` = `VK_SUBTRACT`; `.` and `NumDecimal` follow the layout (documented); every input carries `wScan` from `MapVirtualKeyW(vk, MAPVK_VK_TO_VSC_EX)`. The grid is in half-key units: `gridColumns: 6` = three standard (span-2) keys per row (renamed from `columns` at the final gate so the unit is explicit); the profile reference and the `profile-bound` error text say so. All keys are sent as virtual-key codes (never Unicode/`VK_PACKET`); arrows, Home/End/PageUp/PageDown and Delete carry the extended-key flag. On Windows the production `KeySink` calls `SendInput` directly through the `windows` crate (same version Tauri depends on, per `cargo tree`) so the flags are explicit; `enigo` is kept for the macOS sink (Phase 2).
Later action types: `{ "type": "osc", "host", "port", "address", "args" }`, `{ "type": "qlab", "workspace", "cue" }`, `{ "type": "page", "target" }`. Unknown action types render disabled rather than crash, and unknown JSON fields are ignored, so newer profiles open in older builds.

**Repo layout**
- `src-tauri/src/main.rs`: window setup and geometry (pad size and button rects computed in Rust from the profile formula, not measured in the DOM), Tauri commands (`run_action(buttonId)` only: Rust looks the action up in its own validated profile, never accepts action JSON from the web layer; `load_profile`, async `open_profile`, `reload_profile`, `open_log_folder`, `show_profile_file`, `quit`); `run_action` uses `try_send` and never blocks the main thread
- `src-tauri/src/actions.rs`: serial executor (Windows `KeySink` = `SendInput` via the `windows` crate; enigo is the macOS sink, Phase 2). The synchronous `run_action` command pushes onto one `mpsc` channel consumed by a single worker thread, so taps run in order and never interleave; key output goes through a `KeySink` trait (SendInput on Windows, a recording mock in tests); one press is one `SendInput` batch, which cannot interleave with other input, so modifiers can only stick on a short insert count: then the worker sends key-ups only for keys that batch pressed, never for keys the user physically holds; after each batch the foreground is checked again and a change reports `sideEffects: unknown`; `run_action` returns an error if the worker channel is closed; the queue holds at most 4 pending actions (extra taps flash the key and are logged as dropped) and drops queued actions older than 750 ms; buttonId resolves to an `Arc<Action>` when the tap is queued, so a reload cannot change a queued action; a second tap on the running button within 300 ms of the first always queues (double tap on Down×10 = 20 presses, whatever `intervalMs` is), a later tap cancels the rest of the repeat; tapping the profile name in row 1 stops everything (cancel running, clear queue); an `EVENT_OBJECT_FOCUS` change inside the target window also aborts the running action; press timing uses a `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` timer (plain `sleep(25ms)` is ~31 ms on Windows); `wScan` is masked to the low byte with `KEYEVENTF_EXTENDEDKEY` set from the `0xE0` prefix; Quit cancels the queue, finishes or aborts the current press with modifiers released and exits within 1 s; log lines go to a separate writer thread so file I/O never delays presses; release profile sets `panic = "unwind"` explicitly; the action's target is defined per focus tier: tiers 1-2 use the foreground window at action start; tier 3 uses the last non-pad foreground window from the shared hook, calls `SetForegroundWindow(target)` and waits (polling up to 100 ms) until `GetForegroundWindow() == target`; before every press the worker compares the foreground window with that target and aborts the rest of the action on a mismatch; in tiers 1-2 it refuses to send when the target is the pad (`target-is-pad`); foreground reads go through a `ForegroundProbe` trait (Windows impl in `focus_win.rs`, mock in tests); a short `SendInput` insert count is an error and runs the modifier-release path; tap-again cancel sets an atomic flag the worker checks between presses (not a queued action), and the header shows "cancelled n/N"; emits `action-progress {buttonId, n, N}` and `action-result {buttonId, ok, error}` events (E2)
- `src-tauri/src/combo.rs`: combo grammar parser to virtual-key codes with extended-key flags
- `src-tauri/src/profile.rs`: the only profile parser/validator (serde, defaults, bounds, combo grammar, Win-key gate); on first run copies the bundled R1 profile into the app config dir; remembers the last-used path in `settings.json` there; a failed reload keeps the last valid profile and reports the error; a failed initial load falls back to the embedded R1 profile as a persistent amber "(fallback)" warning (E4, E6); first run writes the starter from the `include_str!` copy (no `bundle.resources`)
- `src-tauri/src/log.rs`: append-only action log in the app data dir: UTC timestamp, button id/label, action JSON, target `{title, isPad, elevated}` at send time, ok/error/dropped/cancelled/aborted; `target-elevated` (ok:false) is logged only when the target's integrity level is higher than the pad's own (captured at startup), because UIPI drops those keys silently; an unreadable token is logged as the warning `target-elevation-unknown`, not a failure. The worker itself captures title and elevation (`GetForegroundWindow`, `GetWindowTextW`, token query), so the log works even if step 7 is dropped (E3). The startup line also records the WebView2 runtime version (evergreen updates can change focus behaviour); the README notes that logs contain window titles
- `src-tauri/src/focus_win.rs` (`cfg(windows)`): tier 2/3 focus code and one `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` hook shared by tier 3 and the target indicator; the hook is installed on the main thread in Tauri `setup` (it needs that thread's message loop); elevation: open the target with `PROCESS_QUERY_LIMITED_INFORMATION`, read `TokenElevation`; `target-elevated` = target elevated and pad not elevated; when the token query is denied, a direct UIPI probe (`PostMessageW(target, RegisterWindowMessageW("tsp-probe"))` failing with `ERROR_ACCESS_DENIED`) decides `target-elevated`, otherwise `unverified`; tier 3 never restores shell windows (`Shell_TrayWnd`, `Progman`, `WorkerW`, `Windows.UI.Core.CoreWindow`); window titles come from `GetWindowTextW` only (never `WM_GETTEXT`, which a hung app can block); the WebView2 user-data folder is separate per elevation level (an elevated run must not break later normal runs); pushes `target-changed {title, isPad, elevated}` events (E5)
- `src/pad.ts`: renders the validated profile; `pointerdown` from pen, mouse or finger triggers the action only when `e.button === 0 && e.isPrimary` (pen barrel button and eraser never fire); finger touches are ignored while a pen is in range (pen `pointerover`/`pointerleave`) and when the contact is wider than ~20 mm (palm), and entirely when a profile sets `acceptTouch: false`; shows `n/N` progress from events; default WebView2 context menus disabled (pen press-and-hold and barrel button), `user-select: none`, `touch-action: none`, no zoom
- `src/header.ts`: renders the canonical Header state table (Pad UI specification) and the in-pad menu; Open profile… turns off always-on-top while the async dialog is open and restores it after
- `src/profile.ts`: calls the Rust commands and renders results; no validation in TypeScript
- `profiles/r1-delay-gain.tsp.json` (Tuesday); `profiles/compass-delay-gain.tsp.json` (Phase 2)
- `.github/workflows/windows-build.yml`: Windows build (`npm run tauri build` + `actions/upload-artifact`) + `cargo test` (E1); tauri-action is used only for tagged releases (Phase 2)
- Plugins/config: `tauri-plugin-dialog` and `tauri-plugin-opener` are called from Rust commands only and are not granted to the webview; the commands themselves only reveal the active profile path or the log directory (Rust-side plugin calls are not limited by webview capability scopes); the R1 profile is embedded with `include_str!` only
- Focus tier selection: all three tiers are compiled into one exe and chosen by the launch flag `--focus-mode=1|2|3` (or env `TSP_FOCUS_MODE`; default from `settings.json`), so one build covers the whole spike. There is no in-app restart: `app.restart()` collides with the single-instance plugin, and `focusable` is fixed at window creation. Tier 2 subclasses the top-level window only (WebView2 render windows live in `msedgewebview2.exe`); the spike records whether setting `WS_EX_NOACTIVATE` on the WebView2 child windows works
- Window/capabilities: opaque window (no `transparent`), Windows 11 rounded corners via `DwmSetWindowAttribute(DWMWA_WINDOW_CORNER_PREFERENCE)`; `core:window:allow-start-dragging` granted for the drag grip; `tauri-plugin-single-instance`: a second launch makes the running pad flash its header (no focus change) and exits; a top-level subclass is installed in every tier for `WM_DISPLAYCHANGE`, `WM_DPICHANGED` and `WM_SETTINGCHANGE`/`SPI_SETWORKAREA`; the pad re-docks only if it would be off-screen or has not been dragged this session (logged); a renderer heartbeat from TS reloads the webview and logs it if WebView2 crashes (blank pad after sleep/GPU reset); an elevated pad adds a `ChangeWindowMessageFilterEx` rule so a non-elevated second launch can still trigger the header flash

**Visual design (approved)**
- Default theme **C, low-glare outline**: dark near-opaque pad (alpha ≥ 0.95), near-transparent keys with a 2px outline in the group colour, labels in the group colour. Keeps emitted light low for dark-adapted eyes at FOH.
- **B, flat colour blocks**, ships as a second built-in theme in Phase 2 (solid group fills, bold labels).
- Group colours: numbers neutral, Enter/Tab blue, fine nudges teal, x10 nudges amber, Undo/Redo muted. Repeat keys show an `xN` badge, and while firing show `n/N` plus a progress bar.
- Themes are sets of CSS custom properties (`--pad-bg`, `--num-bg`, `--ent-fg`, ...). The mockup HTML already uses this token structure, so it carries straight into `src/themes/`. Per-button `color` in a profile overrides the theme's group colour.
- Key size about 92x78 CSS px (about 17x15 mm on a Surface Pro at 200% scaling; about 13 mm at 150%; the startup log line records the DPI scale).

**Pad UI specification (design review, 2026-11-08)**
- **Height policy:** pad height = min(content height, work-area height − 24 px). If the content is taller, all rows shrink evenly to a floor of 56 CSS px and a warning is raised; the pad never scrolls. With the 10-row R1 profile on a Surface Pro 8-11 (888 px usable) rows land at about 74 px; on a Surface Pro 7 (840 px) at about 69 px.
- **Placement:** overlay, docked right, top edge 12 px below the work-area top; R1 is expected to run maximised behind it, so the pad covers its right ~318 px (R1's title-bar buttons stay reachable in the 12 px strip only if R1 is not maximised; reserving screen space as a Windows AppBar is a Phase 2 option, TODOS.md). `···` menu has "Dock right"; Reload keeps the current position.
- **Background:** CSS cannot blur what is behind a window, so theme C uses `--pad-bg` alpha ≥ 0.95 and no `backdrop-filter`; the window itself is opaque with DWM rounded corners. Native acrylic (`window-vibrancy`) is a Phase 2 option, checked on the Surface first.
- **Header:** 40 px tall. Row 1: grip strip (full header height, ≥ 24 px tall hit area), profile name (13 px, ellipsis), `···` button with a 40×40 hit target and an amber dot when warnings exist. Row 2 (16 px): "→" glyph + target window title, 13 px, middle ellipsis. **Canonical header state table (the only source for row-2 colour; supersedes every other mention):**
  | State | Colour | Enters when | Clears when |
  |---|---|---|---|
  | Idle (Tuesday) | row 2 empty | no failure pending | — |
  | Last action refused: pad / untitled / elevation unknown / app not in `targetApps` | amber (code + short text) | `action-result` refused/unverified | next successful action |
  | Last action hit a more-elevated target | red ("target elevated: keys will be dropped") | `action-result` with `target-elevated` | next successful action |
  | Last action failed | red (code + short text) | `action-result` with ok:false | next successful action, or a `target-changed` ≥ 4 s after the failure (never the change that caused an abort) |
  | Profile fallback / load warnings | amber dot on `···` + row-1 suffix "(fallback)" | load failure | a profile loads |
  Red beats amber; the most recent red wins. `target-changed` events are emitted from Tuesday (they drive tier 3 and the red-clear rule) but are not displayed until Phase 2, which adds the live target-window title in row 2 (final gate d7). The header state is a pure Rust reducer `(state, event, now) → state` that emits the rendered row; TS only draws it.
- **Keys:** groups are a fixed enum `num|ent|fine|coarse|hist|custom` (Tab is `ent`); `custom` uses the neutral `num` tokens unless `color` is set. Per-button `color` sets fg = color, border = color, bg = color at 6% alpha, with a log warning when it is below 3:1 against the pad background. Optional `icon` from a built-in set (`up|down|left|right|enter|tab|undo|redo`) renders before the label; a `Ctrl+`/`Shift+` prefix in a label renders as small 13 px text. The repeat badge `×N` is generated whenever `repeat > 1` (starter labels are "Up"/"Down", not "Up x10"). Labels shrink from 25 px to a 13 px floor, wrap to 2 lines, then ellipsis; validation warns when the floor still does not fit. CSS classes are generated as `span-N` from the profile (the mockup's `.w2`/`.w4`/`.w6` are not copied).
- **Key states:** idle; pressed (~120 ms fill using the group's bg token at higher alpha, per group); running (`n/N` badge + progress bar; "tap to stop" shown only when total run time > 500 ms); queued (dim pulse); ok (none beyond pressed); cancelled (`7/10 ✕` in the badge slot for 1.5 s); failed/aborted/dropped (600 ms red outline pulse on the tapped key, `7/10 !` for aborted runs, detail in header row 2); disabled (dashed 1 px outline, label at 40% opacity, small "!" corner; tapping shows the reason in row 2 and sends nothing). Red is reserved for failures and used by no group.
- **Touch:** finger taps fire like pen taps by default (final gate d5); with `acceptTouch: false` a finger tap sends nothing and row 2 briefly shows "Pen only: enable touch in the profile".
- **Menu:** renders inside the pad window (no native popup, which would take focus); rows ≥ 48 px: warnings list (if any), Last error (if any), Reload profile, Open profile…, Show profile file, Open log folder, Dock right / Dock left, divider, Quit. It closes on a second tap of `···`, after a selection, or after 5 s. Quit needs a confirming second tap within 3 s. After Open profile… closes, row 2 shows the real target, so it is amber until R1 is focused again.
- **Contrast (theme C, measured against the effective pad background):** `--num-border` lifted from `#4a5059` (2.21:1) to `#6b7280`, `--hist-border` from `#3a3f46` (1.69:1) to `#5a606a`, `--hist-fg` raised to ≥ 4.5:1; labels ≥ 4.5:1 and outlines ≥ 3:1 for every group. With pad alpha ≥ 0.95 these hold over light apps (Compass) too.
- **Error and message contract (DX review):** every failure has a stable kebab-case code (`profile-syntax`, `profile-bound`, `profile-schema-too-new`, `key-unknown`, `action-unknown`, `system-key-blocked`, `target-is-pad`, `target-elevated`, `target-elevation-unknown`, `aborted-focus-change`, `send-incomplete`, `dropped-queue-full`, `worker-stopped`, `internal-error`, `log-unwritable`, `settings-unreadable`, `sink-unavailable`, `target-not-allowed`, `target-untitled`, `profile-too-large`, `profile-not-utf8`), documented in the README "Error codes" section with `#code` anchors. Rust→TS errors are `Result<T, AppError>` serialised as `{code, message, fix, sideEffects: none|partial|unknown, sent?: n, of?: N}`; TS renders only these fields. Profile errors use `<code> <file>: <locator>: <actual vs allowed>. <fix>` (locator = `buttons[3] "Down"` or serde line/column), e.g. `profile-bound r1.tsp.json: buttons[3] "Down".repeat = 80 (allowed 1-50). Set repeat ≤ 50, then ··· → Reload.` Row 2 shows code + short form (`aborted 7/10: focus → Teams`); the full text, side effects and next step go to a `···` → "Last error" row and the log line (with expected vs actual target titles), e.g. `aborted-focus-change: 7/10 sent (focus moved to "Teams"). Value changed by 7; check before retrying.`, `send-incomplete: outcome unknown, modifiers released; check the R1 field before retrying`, `target-is-pad: nothing sent. Tap the R1 field first, then retry.`, `target-elevated: keys will be dropped. Quit, then start the pad with Run as administrator.` Red/amber behaviour follows the canonical header state table. An unverifiable target (`target-elevation-unknown`) gives outcome `unverified`: an amber key pulse, not the plain pressed state. Profile load failures and the bundled-profile fallback are persistent warnings (amber dot, warnings list with full message and path, row-1 suffix "(fallback)") until a profile loads. A `std::panic::set_hook` writes message, location and backtrace to `<logdir>/crash-<ts>.txt`; row 2 then shows `internal-error: see crash-…txt (··· → Open log folder). Quit and relaunch.`; failures before the window exists show one native `MessageBoxW` at launch with what failed, the crash file path and the fix (e.g. the WebView2 Runtime URL). The log serialiser redacts `passcode`, `password` and `token` fields. `settings.json` unreadable → defaults + warning with path and parse error, never a failed start. A second launch makes the running pad flash its header for 1 s (no focus change).
- **Accessibility scope:** the window is non-focusable by design, so keyboard navigation does not apply; keys carry `aria-label` (label + action) for screen readers; targets are ≥ 56 CSS px tall even after shrinking.
